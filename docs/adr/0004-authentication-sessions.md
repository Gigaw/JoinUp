# ADR 0004: Аутентификация и серверные сессии

- **Статус:** Принято
- **Дата:** 2026-08-03
- **Связанные Issues:** [#1](https://github.com/Gigaw/JoinUp/issues/1), [#3](https://github.com/Gigaw/JoinUp/issues/3), [#11](https://github.com/Gigaw/JoinUp/issues/11)
- **Заменяет:** —
- **Заменено:** —

## Контекст

Первый каркас поддерживает регистрацию и вход по email и паролю, выход и восстановление сессии
после перезапуска приложения. Подтверждение email, восстановление пароля и управление сессиями на
других устройствах отложены. Backend обязан проверять возраст 18+ и не раскрывать дату рождения.

## Критерии решения

- безопасное хранение паролей и токенов;
- немедленный отзыв сессии при выходе;
- простая реализация для мобильного клиента;
- возможность позднее добавить управление устройствами;
- отсутствие персональных данных и секретов в логах.

## Рассмотренные варианты

### Непрозрачные серверные сессии

Клиент хранит случайный токен, а backend — только его хеш и состояние сессии. Каждый защищённый
запрос требует поиска сессии в базе, зато отзыв и проверка срока действия происходят немедленно.

### Короткоживущий JWT и refresh token

Снижает необходимость обращения к хранилищу для каждого запроса, но добавляет ротацию refresh
token, две модели срока жизни и период, в котором отозванный access token остаётся действительным.

### Внешний identity provider

Уменьшает объём собственной auth-логики, но добавляет внешний сервис и не требуется для выбранного
email/password сценария первого каркаса.

## Решение

Использовать непрозрачные серверные сессии:

- пароль хешируется Argon2id; исходный пароль никогда не сохраняется и не журналируется;
- после входа backend создаёт криптографически случайный токен достаточной энтропии;
- мобильное приложение хранит токен в Expo SecureStore;
- запрос передаёт токен в заголовке `Authorization: Bearer <token>`;
- backend хранит только хеш токена, `userId`, срок действия, время создания и отметку отзыва;
- NestJS Guard проверяет сессию и передаёт идентификатор пользователя в application-слой;
- выход отзывает текущую сессию;
- точные сроки жизни и политика продления задаются конфигурацией до реализации и тестируются.

Регистрация проверяет корректность email, минимальную длину пароля и совершеннолетие на backend.
Дата рождения хранится как приватное поле. Публичный возраст рассчитывается backend на момент
ответа и возвращается только при включённой пользователем настройке видимости.

Таблица сессий является точкой расширения для будущего управления устройствами, но endpoints для
просмотра и отзыва других сессий в первый каркас не входят.

## Последствия

### Положительные

- logout прекращает действие токена немедленно;
- утечка базы не раскрывает активные session tokens;
- mobile работает с одним типом токена;
- модель естественно расширяется метаданными устройства и управлением сессиями.

### Отрицательные и риски

- каждый защищённый запрос проверяет сессию в PostgreSQL;
- компрометация токена даёт доступ до его отзыва или истечения срока;
- rate limiting для регистрации и входа всё равно необходим и будет описан в backend-архитектуре;
- добавление кеша сессий допускается только после измерений и отдельного ADR.

## Проверка соблюдения

- auth-тесты покрывают неверный пароль, истёкшую и отозванную сессию;
- тесты регистрации проверяют возраст ровно на границе 18 лет;
- тесты публичных API подтверждают отсутствие даты рождения;
- конфигурация логирования редактирует `Authorization`, пароль, токен и дату рождения;
- токен на устройстве сохраняется только через SecureStore.
