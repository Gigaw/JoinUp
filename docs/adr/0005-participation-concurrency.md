# ADR 0005: Модель участия и конкурентное занятие места

- **Статус:** Принято
- **Дата:** 2026-08-03
- **Связанные Issues:** [#1](https://github.com/Gigaw/JoinUp/issues/1), [#3](https://github.com/Gigaw/JoinUp/issues/3), [#9](https://github.com/Gigaw/JoinUp/issues/9), [#11](https://github.com/Gigaw/JoinUp/issues/11)
- **Заменяет:** —
- **Заменено:** —

## Контекст

Организатор всегда считается участником. Ожидающие заявки не резервируют место. Автоматическое
присоединение и подтверждение заявки могут одновременно пытаться занять последнее место, а
повторные сетевые запросы не должны создавать дубликаты. После заполнения события все оставшиеся
`pending` заявки автоматически становятся `rejected` и позднее не восстанавливаются.

## Критерии решения

- не более `capacity` записей со статусом `going`, включая организатора;
- одна текущая связь пользователя с событием;
- безопасные retry и параллельные запросы;
- атомарное отклонение оставшихся заявок при заполнении;
- запрет изменений после начала или отмены события.

## Рассмотренные варианты

### Блокировка строки события и подсчёт подтверждённых участников

Каждая операция сначала блокирует событие, затем проверяет и изменяет participation-записи в одной
транзакции. Решение просто проверяется и не требует поддерживать отдельный счётчик.

### Атомарный счётчик занятых мест в событии

Условный `UPDATE` счётчика может быстро занимать место, но создаёт дополнительное производное
состояние, которое нужно синхронизировать при каждом переходе и восстанавливать при расхождении.

### Проверка вместимости только в application-коде

Обычный запрос количества участников без блокировки допускает, что два запроса одновременно увидят
одно свободное место и оба завершатся успешно.

## Решение

Хранить одну текущую participation-запись на пару `(eventId, userId)` с уникальным ограничением и
одним из статусов `pending`, `going`, `rejected`, `withdrawn` или `cancelled`. Если позднее понадобится
полный аудит переходов, он хранится в отдельном append-only журнале, а не в дубликатах текущей
связи.

Создание события и participation организатора со статусом `going` выполняются одной транзакцией.
Вместимость всегда включает организатора и не может быть меньше двух.

Все операции join, apply, approve, reject, withdraw, cancel participation, cancel event и изменение
capacity выполняются по единому протоколу:

1. начать транзакцию;
2. заблокировать строку события через `SELECT ... FOR UPDATE`;
3. повторно проверить статус события, время начала, владельца, режим участия и текущий статус
   participation;
4. посчитать записи `going` и проверить capacity;
5. выполнить допустимый переход состояния;
6. если занято последнее место, в той же транзакции перевести остальные `pending` в `rejected`;
7. завершить транзакцию.

Каждый путь записи блокирует событие до изменения participation, поэтому операции для одного
события сериализуются. Внутри транзакции запрещены сетевые вызовы.

Повтор операции, когда требуемое целевое состояние уже достигнуто, возвращает актуальный успешный
результат. Недопустимый переход возвращает конфликт без изменения данных. Для операций, которые
могут создать независимый ресурс повторным запросом, включая создание события, API использует
`Idempotency-Key` и серверное хранилище результатов операции.

## Последствия

### Положительные

- два пользователя не могут занять одно последнее место;
- уникальное ограничение защищает от дубликатов независимо от application-кода;
- заполнение и отклонение ожидающих заявок атомарны;
- отсутствие кешированного счётчика уменьшает количество состояний, которые могут разойтись.

### Отрицательные и риски

- записи для одного популярного события обрабатываются последовательно;
- row lock требует SQL внутри Prisma-транзакции;
- каждый переход должен следовать одному протоколу, иначе гарантия сериализации нарушается;
- правила повторной подачи после `withdrawn` или `rejected` должны быть явно определены в API и
  data model до реализации соответствующего перехода.

## Проверка соблюдения

- интеграционный тест запускает минимум две одновременные попытки занять последнее место;
- тест подтверждения последнего места проверяет автоматический перевод остальных заявок в
  `rejected`;
- retry-тесты проверяют отсутствие дублей и стабильный ответ;
- тесты проверяют запрет изменений после начала и отмены события;
- миграция содержит уникальное ограничение `(eventId, userId)`.
