# ADR 0009: Тестовое развёртывание API на одиночном VPS

- **Статус:** Принято
- **Дата:** 2026-08-27
- **Связанные Issues:** [#51](https://github.com/Gigaw/JoinUp/issues/51)
- **Заменяет:** —
- **Заменено:** —

## Контекст

API первого рабочего каркаса до этого запускался только локально. Для проверки mobile-клиента на
реальных устройствах нужен доступный по HTTPS backend, но постоянный домен, CI/CD, внешний registry
и резервное хранилище ещё не выбраны.

У проекта есть один существующий Ubuntu VPS с Docker Compose, открытыми портами 80 и 443 и
ограниченными ресурсами. До начала работ на нём работало неактуальное приложение, ресурсы которого
владелец явно разрешил удалить. В соответствии с ADR 0007 API остаётся одним экземпляром и хранит
изображения в локальном persistent volume.

## Критерии решения

- HTTPS без добавления нового платного провайдера для технического теста;
- PostgreSQL и `MEDIA_ROOT` переживают перезапуск контейнеров;
- база данных не доступна из интернета;
- Prisma migration выполняется отдельно до старта API;
- секреты не попадают в Git и не передаются в Docker image;
- решение сохраняет прямой путь к постоянному домену, backup и CI/CD.

## Рассмотренные варианты

### Один VPS, Docker Compose и Caddy

API, PostgreSQL и Caddy работают в одном Compose-проекте. Caddy принимает внешний трафик и
автоматически получает сертификат. PostgreSQL доступен только через внутреннюю Docker-сеть, а база,
изображения и состояние Caddy находятся в named volumes.

Временный hostname `sslip.io` позволяет проверить HTTPS до покупки или подключения постоянного
домена. Решение не добавляет отдельный hosting provider и подходит для одного API-экземпляра.

### Managed hosting и managed PostgreSQL

Уменьшает задачи системного администрирования и обычно даёт backup из коробки, но требует выбрать
провайдера, создать новую учётную запись и оплачивать ещё один сервис до подтверждения технического
сценария.

### Процессы на хосте без Docker Compose

Уменьшает число контейнеров, но смешивает зависимости приложения с ОС, усложняет воспроизводимость
и не соответствует уже принятому локальному Docker-подходу для PostgreSQL.

## Решение

Для технического теста использовать один существующий VPS и Docker Compose из `infra/`:

- Caddy публикует только TCP-порты 80 и 443 и проксирует запросы к единственному API;
- API запускается непривилегированным пользователем и подключён к публичной Docker-сети только для
  связи с Caddy; PostgreSQL доступен API и operation-контейнерам через отдельную internal-сеть;
- `postgres-data`, `media-data`, `caddy-data` и `caddy-config` — persistent named volumes;
- migration и initial catalog seed запускаются как одноразовые operation-контейнеры до API;
- файл `.env.test` существует только на VPS с правами доступа владельца и содержит URL-safe случайный
  пароль PostgreSQL;
- временный hostname — `31-128-42-29.sslip.io`; при появлении постоянного домена меняется только
  `API_HOST` и mobile build-time переменная `EXPO_PUBLIC_API_URL`.

Тестовое окружение допускает только тестовые учётные записи и данные, которые могут быть сброшены.
Оно не является публичным пилотом: до него нужны постоянный домен, независимые резервные копии,
реализованный rate limiting auth-endpoints и safety-возможности из PRD. CI/CD, registry, S3 и
горизонтальное масштабирование намеренно не входят в это решение.

## Последствия

### Положительные

- mobile-клиент может обращаться к API по HTTPS с реального устройства;
- PostgreSQL и локальные изображения сохраняются при redeploy;
- наружу не публикуются PostgreSQL, API-порт или `MEDIA_ROOT`;
- конфигурация запуска, migration и проверок находится в репозитории, а секреты — нет;
- переход на собственный домен не требует изменения API-контракта.

### Отрицательные и риски

- VPS остаётся единой точкой отказа, а небольшой диск ограничивает image build, database и media;
- `sslip.io` не является доменом, которым владеет проект, и не подходит для бренда или долгой
  эксплуатации;
- named volumes на одном VPS не заменяют независимые backup;
- один filesystem volume сохраняет ограничение ADR 0007 на единственный API-экземпляр;
- внешний HTTP endpoint доступен из интернета, поэтому до публичного пилота нельзя принимать реальные
  пользовательские данные.

## Проверка соблюдения

- `docker compose ... config --quiet` проверяет Compose-конфигурацию до запуска;
- image собирается из `infra/Dockerfile.api`, а migration и catalog seed проходят до запуска API;
- API health check проверяет PostgreSQL и writable `MEDIA_ROOT`;
- внешняя проверка `https://<host>/v1/health/ready` подтверждает TLS и readiness;
- `docker compose ps`, `docker volume ls` и firewall-проверка подтверждают, что база не имеет
  опубликованного порта;
- ревью подтверждает отсутствие `.env.test`, паролей и volumes в Git.
