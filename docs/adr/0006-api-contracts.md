# ADR 0006: REST, OpenAPI и типизированный API-клиент

- **Статус:** Принято
- **Дата:** 2026-08-03
- **Связанные Issues:** [#1](https://github.com/Gigaw/JoinUp/issues/1), [#9](https://github.com/Gigaw/JoinUp/issues/9), [#11](https://github.com/Gigaw/JoinUp/issues/11)
- **Заменяет:** —
- **Заменено:** —

## Контекст

Mobile и backend написаны на TypeScript, но не должны разделять внутренние domain-модели. API
должен иметь проверяемый runtime-контракт, документировать ошибки и идемпотентность и оставаться
понятным для будущих клиентов, не использующих TypeScript.

## Критерии решения

- типобезопасность запросов и ответов в mobile;
- runtime-валидация входных данных на backend;
- независимый и версионируемый HTTP-контракт;
- отсутствие ручного дублирования API-интерфейсов;
- автоматическая проверка расхождений в CI.

## Рассмотренные варианты

### REST, NestJS DTO и OpenAPI

NestJS валидирует DTO и формирует OpenAPI-документ, из которого создаётся клиент. Подход сохраняет
стандартный HTTP-контракт, но требует детерминированной генерации и проверки схемы.

### tRPC

Даёт прямой вывод TypeScript-типов, но связывает mobile с реализацией router на backend и делает
контракт менее удобным для других платформ.

### Общий пакет вручную написанных TypeScript-типов

Прост в начале, но типы не обеспечивают runtime-валидацию и могут разойтись с фактическими route и
сериализацией.

## Решение

Использовать JSON REST API под префиксом `/v1`. Transport DTO и NestJS decorators являются
исходными данными для OpenAPI-документа. Входные DTO проходят runtime-валидацию в глобальном
ValidationPipe с запретом неизвестных полей и неявного доверия клиентским данным.

Из детерминированно сформированного OpenAPI-документа `openapi-typescript` генерирует типы в
`packages/api-client`, а `openapi-fetch` предоставляет небольшой типизированный HTTP-клиент.
Mobile импортирует только публичный API этого пакета и не зависит от backend DTO, Prisma-моделей
или domain-сущностей.

OpenAPI должен описывать:

- успешные ответы и все ожидаемые ошибки;
- authentication requirements;
- pagination и filters;
- заголовок `Idempotency-Key` для соответствующих операций;
- nullable и optional поля без неоднозначности;
- отдельные публичные user projections без даты рождения.

Единый формат прикладной ошибки содержит стабильный машинный `code`, безопасное сообщение,
необязательные field details и `requestId`. Полный перечень кодов и endpoint-ов определяется в
`docs/architecture/api-contracts.md`.

## Последствия

### Положительные

- mobile получает типы без импорта внутреннего кода backend;
- OpenAPI можно использовать для документации, тестов и будущих клиентов;
- runtime-валидация и compile-time типы происходят из одного transport-описания;
- breaking changes видны в diff схемы и сгенерированного клиента.

### Отрицательные и риски

- NestJS metadata и Swagger decorators должны полно описывать сериализацию;
- генерация добавляет обязательный шаг после изменения DTO;
- TypeScript-тип не заменяет обработку runtime-ошибок и нестабильной сети;
- случайное включение внутреннего поля в DTO может раскрыть данные, поэтому privacy-проекции
  проверяются отдельными тестами.

## Проверка соблюдения

- CI генерирует OpenAPI и `api-client` и завершается с ошибкой при незакоммиченном diff;
- contract-тесты проверяют реализацию ключевых ответов и ошибок;
- архитектурное правило запрещает mobile импортировать `apps/api`;
- тесты публичных user и participant endpoints подтверждают отсутствие `birthDate`;
- изменение `/v1` проходит ревью на обратную совместимость.
