# ADR 0003: PostgreSQL и Prisma для хранения данных

## Контекст

Данные пользователей, событий и участия связаны между собой и требуют транзакций, уникальных
ограничений и безопасной обработки одновременных запросов на последнее место. Дата рождения
является приватными данными, поэтому доступ к пользовательским записям должен проходить через
явные прикладные сценарии и DTO.

## Критерии решения

- реляционные ограничения и транзакции;
- предсказуемая конкурентная запись;
- типизированный доступ из NestJS;
- управляемые и рецензируемые миграции;
- возможность использовать возможности PostgreSQL, отсутствующие в ORM.

## Рассмотренные варианты

### PostgreSQL и Prisma

Prisma предоставляет типизированный клиент и миграции, а PostgreSQL — необходимые транзакции,
блокировки и индексы. Для части ограничений и блокировок потребуется SQL внутри миграций и
persistence-адаптеров.

### PostgreSQL и Drizzle

Drizzle ближе к SQL и удобен для сложных запросов, но выбранный NestJS-вариант выигрывает от более
распространённого интеграционного пути и учебной ценности Prisma.

### SQLite для первого каркаса

Упрощает локальный запуск, но не воспроизводит конкурентное поведение, блокировки и ограничения,
на которые опирается модель участия.

## Решение

Использовать PostgreSQL как единственную production-подобную реляционную базу и Prisma для схемы,
миграций и обычных запросов.

Доступ к Prisma сосредоточен в persistence-слое backend. Контроллеры и domain-код не обращаются к
`PrismaClient` напрямую. Миграции хранятся в репозитории и могут включать проверенный SQL для
ограничений, индексов и других возможностей, которые нельзя выразить Prisma Schema Language.

Конкурентные изменения участия выполняются в одной Prisma interactive transaction. Блокировка
строки события выполняется параметризованным SQL внутри выделенного repository-метода. Все пути
изменения участия обязаны сначала получать эту блокировку в одинаковом порядке.

Тесты persistence и concurrency запускаются на PostgreSQL. SQLite не используется как замена базы
в интеграционных тестах.

## Последствия

### Положительные

- доменные инварианты защищены как application-логикой, так и базой данных;
- типизированный клиент покрывает большинство запросов;
- тестовая среда воспроизводит production-семантику транзакций;
- raw SQL ограничен небольшим числом рецензируемых persistence-методов и миграций.

### Отрицательные и риски

- для локальной разработки и CI нужен PostgreSQL;
- команда должна понимать границы транзакций и SQL-блокировок, а не полагаться только на ORM;
- обновления Prisma требуют проверки сгенерированных миграций;
- долгие транзакции могут создавать очередь ожидания на популярном событии, поэтому внутри
  блокировки нельзя выполнять сетевые вызовы.

## Проверка соблюдения

- миграции применяются к чистой PostgreSQL-базе в CI;
- интеграционные тесты проверяют уникальность, вместимость и одновременное занятие последнего места;
- использование raw SQL допускается только в persistence-слое и миграциях;
- запросы не возвращают дату рождения через публичные projections.
