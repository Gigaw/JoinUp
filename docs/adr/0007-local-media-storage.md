# ADR 0007: Локальное хранение изображений первого каркаса

- **Статус:** Принято
- **Дата:** 2026-08-04
- **Связанные Issues:** [#1](https://github.com/Gigaw/JoinUp/issues/1), [#9](https://github.com/Gigaw/JoinUp/issues/9), [#13](https://github.com/Gigaw/JoinUp/issues/13)
- **Заменяет:** —
- **Заменено:** —

## Контекст

Профиль и событие могут иметь по одному изображению. Для первого рабочего каркаса не требуется
подключать внешнее object storage, CDN или отдельный media service, но файлы нельзя хранить в Git,
внутри application image или непосредственно в PostgreSQL.

## Критерии решения

- минимальное количество инфраструктурных компонентов;
- безопасные имена, типы и ограничения файлов;
- сохранение изображений после перезапуска API;
- понятная граница будущей миграции в object storage;
- отсутствие бинарных данных в PostgreSQL и резервных копиях основной базы.

## Рассмотренные варианты

### Локальный persistent-каталог API-сервера

Не требует внешнего сервиса и подходит для одного экземпляра API. Ограничивает горизонтальное
масштабирование и требует отдельного резервного копирования каталога.

### S3-совместимое object storage

Поддерживает несколько API-инстансов, signed uploads и независимое масштабирование, но добавляет
внешний сервис, credentials и lifecycle configuration раньше, чем это нужно каркасу.

### Бинарные данные в PostgreSQL

Даёт единую транзакционную систему хранения, но увеличивает базу и её backups, связывает выдачу
файлов с database connections и усложняет будущую миграцию.

## Решение

Хранить изображения первого каркаса в каталоге, заданном обязательной runtime-переменной
`MEDIA_ROOT`. Каталог находится вне отслеживаемых Git файлов и application image. В
production-like окружении он размещается на persistent volume, который переживает перезапуск API.

PostgreSQL хранит только относительный непрозрачный storage key. Абсолютный путь никогда не
принимается от клиента и не возвращается в API. Backend формирует путь внутри `MEDIA_ROOT` и
запрещает выход за его границы.

Upload endpoint:

- требует authentication и ownership соответствующего профиля или события;
- принимает только документированные image MIME types и проверяет фактическое содержимое;
- принимает JPEG, PNG или WebP до 5 MiB и не более 4096 × 4096 pixels;
- отклоняет animated images и несоответствие заявленного MIME фактическому содержимому;
- создаёт файл во временном каталоге и выполняет atomic rename после полной записи;
- использует сгенерированное backend имя, а не исходное имя клиента;
- обновляет database reference только после успешной записи файла;
- не пишет содержимое и исходное имя файла в логи.

Первый deployment использует один экземпляр API. Несколько экземпляров допустимы только с одним
общим persistent volume и согласованным способом записи. Переход на Amazon S3 вынесен в задачу
[#13](https://github.com/Gigaw/JoinUp/issues/13) и требует нового ADR, media adapter и migration
существующих keys без изменения публичных DTO.

## Последствия

### Положительные

- изображения работают без нового внешнего сервиса;
- PostgreSQL остаётся хранилищем metadata, а не бинарных файлов;
- opaque storage key позволяет позднее заменить filesystem adapter;
- резервное копирование media можно выполнять отдельно от базы.

### Отрицательные и риски

- локальный диск без persistent volume приведёт к потере изображений при redeploy;
- один локальный каталог ограничивает горизонтальное масштабирование API;
- database transaction и filesystem write не образуют общую атомарную транзакцию;
- необходимы cleanup временных и orphaned files, а также отдельный backup каталога;
- выдача изображений через API создаёт дополнительную нагрузку без CDN.

## Проверка соблюдения

- startup validation отклоняет production-like запуск без доступного writable `MEDIA_ROOT`;
- тесты проверяют MIME type, размер, ownership, path traversal и прерванную загрузку;
- `.gitignore` исключает локальный media-каталог;
- integration test подтверждает сохранность файла после перезапуска API с тем же volume;
- public DTO возвращает URL или media identifier, но не filesystem path.
