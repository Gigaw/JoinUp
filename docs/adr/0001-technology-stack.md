# ADR 0001: Технологический стек первого рабочего каркаса

- **Статус:** Принято
- **Дата:** 2026-08-03
- **Связанные Issues:** [#1](https://github.com/Gigaw/JoinUp/issues/1), [#10](https://github.com/Gigaw/JoinUp/issues/10), [#11](https://github.com/Gigaw/JoinUp/issues/11)
- **Заменяет:** —
- **Заменено:** —

## Контекст

Первый рабочий каркас должен поддерживать iOS и Android, строгую типизацию между мобильным
клиентом и backend, серверную проверку бизнес-правил и постепенное развитие без преждевременного
разделения системы на сервисы. Проект также должен дать практический опыт работы с NestJS.

Точные версии пакетов будут закреплены lock-файлом при создании каркаса. Этот ADR выбирает
технологии и границы их ответственности, но не разрешает начинать scaffolding до завершения
архитектурных документов из задачи #1.

## Критерии решения

- единый язык и строгая типизация на mobile и backend;
- поддержка актуальных iOS и Android через Expo;
- явные модули, авторизация и валидация на backend;
- поддержка транзакций и ограничений PostgreSQL;
- умеренная сложность эксплуатации для первого каркаса.

## Рассмотренные варианты

### NestJS и Prisma

NestJS предоставляет модули, dependency injection, guards, pipes и единый подход к тестированию.
Prisma даёт типизированный доступ к PostgreSQL и управляемые миграции. Цена выбора — больший объём
каркасного кода и необходимость выходить на уровень SQL для отдельных конкурентных операций.

### Fastify и Drizzle без прикладного фреймворка

Вариант даёт меньше абстракций и прямой контроль над SQL, но требует самостоятельно определить и
поддерживать соглашения для модулей, внедрения зависимостей, авторизации и обработки ошибок.

### tRPC и облегчённый Node.js backend

Вариант сокращает путь до сквозной типизации, но сильнее связывает мобильный клиент с реализацией
backend и хуже выражает независимый HTTP-контракт.

## Решение

Использовать следующий стек:

- TypeScript в строгом режиме для всего собственного кода;
- React Native с Expo для мобильного приложения;
- Expo Router для навигации;
- TanStack Query для server state;
- React Hook Form и Zod для мобильных форм и клиентской проверки;
- NestJS с Fastify adapter для backend;
- PostgreSQL и Prisma для постоянного хранения данных;
- REST и OpenAPI для взаимодействия mobile и backend.

Backend реализуется как модульный монолит. Разделение на микросервисы, очередь сообщений, Redis и
real-time транспорт не входят в первый рабочий каркас. Локальное состояние mobile не должно
дублировать server state; отдельная библиотека client state добавляется только при подтверждённой
необходимости.

## Последствия

### Положительные

- NestJS даёт единые соглашения для модулей и защищённых действий;
- Fastify adapter сохраняет лёгкий HTTP-слой;
- TypeScript используется по всей цепочке разработки;
- стек покрывает требования MVP без дополнительных инфраструктурных сервисов.

### Отрицательные и риски

- NestJS добавляет dependency injection и decorators, которые требуют дисциплины в границах слоёв;
- middleware, написанный только для Express, нельзя подключать без проверки совместимости;
- Prisma не выражает все нужные ограничения и блокировки, поэтому часть миграций и конкурентных
  операций будет содержать контролируемый SQL;
- одновременное использование Zod на mobile и NestJS DTO не должно создавать две независимые
  версии API-контракта: источником transport-контракта будет OpenAPI согласно ADR 0006.

## Проверка соблюдения

- корневая конфигурация включает строгую проверку TypeScript;
- backend запускается через NestJS с Fastify adapter;
- зависимости от Express не добавляются без отдельного обоснования;
- CI проверяет форматирование, типы и тесты всех workspace-пакетов.
