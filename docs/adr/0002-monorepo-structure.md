# ADR 0002: Структура монорепозитория

- **Заменено:** —

## Контекст

Мобильный клиент, backend и типизированный API-клиент развиваются совместно и должны проверяться
одним изменением. При этом mobile не должен импортировать внутреннюю доменную модель backend, а
общие пакеты не должны превращаться в неструктурированный набор утилит.

## Критерии решения

- атомарные изменения API и mobile;
- единые версии инструментов и воспроизводимая установка;
- явные направления зависимостей;
- отсутствие дополнительного orchestration-инструмента без измеримой необходимости.

## Рассмотренные варианты

### Отдельные репозитории

Дают независимый жизненный цикл приложений, но усложняют синхронизацию API-контрактов и не дают
заметной выгоды для одной команды и одного продукта на стадии MVP.

### pnpm workspaces

Обеспечивают общую установку, локальные workspace-зависимости и корневые команды без отдельного
слоя orchestration.

### pnpm с Turborepo или Nx

Добавляют граф задач, кеширование и инструменты для больших монорепозиториев, но повышают объём
конфигурации до появления проблемы со скоростью CI или количеством пакетов.

## Решение

Использовать монорепозиторий на `pnpm workspaces` с целевой структурой:

```text
apps/
  api/
  mobile/
packages/
  api-client/
  config/
```

`apps/api` содержит NestJS backend, а `apps/mobile` — Expo-приложение. `packages/api-client`
содержит сгенерированные из OpenAPI типы и клиент. `packages/config` содержит только действительно
общие настройки TypeScript и инструментов.

Mobile может зависеть от `api-client` и `config`. Backend может зависеть от `config`. Mobile не
импортирует код из `apps/api`, а backend не зависит от mobile. Новые общие пакеты создаются только
после появления повторяемой ответственности. Turborepo или Nx на первом этапе не используются.

## Последствия

### Положительные

- изменение endpoint и его потребителя можно проверить в одном pull request;
- установка и lock-файл едины для всего проекта;
- граница сгенерированного API-клиента препятствует импорту backend-моделей в mobile;
- начальная конфигурация остаётся небольшой.

### Отрицательные и риски

- CI сначала выполняет задачи без распределённого кеша;
- неосторожные корневые импорты могут нарушить границы приложений;
- при существенном росте репозитория может потребоваться отдельный task runner, что оформляется
  новым ADR на основании измерений.

## Проверка соблюдения

- workspace-пакеты объявлены в `pnpm-workspace.yaml`;
- импорты между приложениями запрещены настройками линтера или границами package exports;
- корневые команды запускают проверки всех затронутых workspace-пакетов;
- сгенерированный API-клиент проверяется в CI.
